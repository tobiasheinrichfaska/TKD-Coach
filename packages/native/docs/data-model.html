Data Model & Data Manipulation

How TKD-Coach stores its data and the framework-free functions that read and change it. The whole model lives in one persisted object (AppData); all behaviour is driven by data and exercised by a pure, unit-tested domain layer that knows nothing about React.

Generated from source · src/types/index.ts, src/domain/*, src/context/reducer.ts. Keep in sync when the model changes.

Architecture — data-driven, logic/UI separation

Three layers, with a strict one-way dependency. The UI never embeds rules; rules never import the UI.

UI layer
src/screens/*, components
renders + dispatches
→
State layer
DataContext + reducer
holds AppState, persists
→
Domain layer
src/domain/*
pure rules & data

The UI dispatches actions and reads state; the reducer is the only writer of state; the domain layer is pure (no React, no storage, no UI) and is the single source of truth for catalogs, metric schemas, derived values and migration. This satisfies the workspace rule: the logic layer must run and be fully testable without any UI.

Where things live

  • types/index.ts — every interface
  • constants/games.ts — built-in Übungen + template seeds
  • context/reducer.ts — state transitions (the only writer)
  • context/DataContext.tsx — load, migrate, debounced persist
  • domain/* — metrics, catalogs, selectors, templates, migration

Core principle

Adding a metric, technique, body part or template means adding data — not writing new control flow. The assessment form, its validation, and the progress colour are all generated from METRIC_SCHEMAS.

Werkseinstellungen (factory defaults)

The app ships with two kinds of built-in data. They behave differently — know which is which:

Editable seed-once stores

These live in AppData (persisted + synced). migrate() seeds them only when empty (fresh install) and never auto-overwrites afterwards, so user edits stick. isBuiltIn flags the factory rows.

Factory dataWhatSeededEditable?
BUILTIN_GAMES (29 Übungen)The drill library — neuro games (W/M/C) + the mobility/stretch protocol (K/D).Once, on fresh install.Yes — edits persist. A "reset to factory" is planned (Phase 4).
BUILTIN_TEMPLATES (4)kids-2hyouth-adult-1h30mobility-warmupstatic-blockOnce, on fresh install.Yes — edits persist.
Consequence: re-tagging a built-in (e.g. adding neuro abilities to a game) reaches fresh installs only; existing devices keep their seeded copy until they edit it or use the planned factory reset.

Fixed compiled-in reference catalogs

These are constants in the code — not in AppData, not stored or synced. They are identical for every install, always present, and (currently) not user-editable.

CatalogWhatEditable?
BELT_INFOS (23)The Kup/Poom/Dan grade ladder (incl. "keine Graduierung").No (fixed).
BODY_PARTS (32)22 anatomical + 10 neuro-athletic abilities.No today; Phase 4 may make catalogs editable.
TECHNIQUES (47)Kicks/stances/blocks/strikes/footwork + Taegeuk & Yudanja poomsae.No today; Phase 4 candidate.
METRIC_SCHEMAS (6)Assessment metric definitions (fields/units/primary).No (drives the generic form).

Belt normalisation on load maps legacy colour ids to the ladder; otherwise the fixed catalogs are read straight from code.

Person, roles & Group

One Person is the identity (name + reachability). Roles attach by composition, not inheritance: an embedded athlete profile and an isCoach flag. The same person can be an athlete, a coach, and another athlete's guardian simultaneously. The UI keeps "athlete" as a concept via the flat AthleteView read-model.

Integrity is unit-tested: every techniques/bodyParts id used by a built-in Übung, and every itemIds id in a built-in template, must resolve to a catalog/library entry.

Neuro-athletic abilities (vestibular, visual, proprioception, reaction, coordination, balance, working-memory, attention, gaze-stability, recovery) live in the same BodyPart catalog with kind:'neuro' (region 'neuro'), so a game tags them in the ordinary bodyParts field and one coverage dimension spans anatomy + neuro. They replace the retired neuroTarget; the core three (vestibular/visual/proprioception) align with Athlete.neuroProfile. NEURO_ABILITIES exposes just the neuro subset.

A third reference catalog, Belt (constants/belts.ts → BELT_INFOS), is the fixed grade ladder (keine Graduierung, 10→1 Kup, then Poom/Dan — 23 entries) that Athlete.belt points at. It is not user-editable; legacy colour ids are normalised to ladder ids by migration, and movement along it is governed by the age-aware graduation rules.

Data manipulation 1 — Reducer actions

The reducer in context/reducer.ts is the only code that writes state. Every action returns a new state object (immutable; never mutates the previous one). Dispatch via useData().dispatch.

ActionPayloadEffect
SET_LOADEDbooleanToggle the loaded flag.
LOAD_ALLAppDataReplace whole state; set isLoaded=true.
ADD_GROUP / UPDATE_GROUPGroupAppend / replace by id.

Data manipulation 6 — Graduation rules domain/graduation.ts

Belt movement is computed, not free-set. Because only the birth year is known, age is a 1-year range, so the rules use "definitely" bounds (refYear = current year):

HelperMeaning
definitelyUnder15max age (refYear − birthYear) ≤ 14
definitely14OrAbovemin age (refYear − birthYear − 1) ≥ 14
definitely15OrAbovemin age ≥ 15
FunctionSignatureRule
ageFacts(birthYear?, refYear) → {3 bounds}Unknown birth year ⇒ nothing is "definite".
promote(belt, birthYear?, refYear) → Belt | nullWalks none→Kup; 1.Kup→Dan only when definitely15OrAbove, else →Poom; Poom→Poom (never Dan) and not at all once 15+; Dan up to 9. null = no promotion available.
demote(belt) → Belt | nullReverse along the spine; 1.Poom/1.Dan→1.Kup; none→null.
canConvertToDan(belt, birthYear?, refYear) → booleanTrue only for a Poom once definitely14OrAbove.
convertToDan(belt) → Belt | nullpoom-N → dan-N.

The athlete editor shows only the stored grade plus Graduieren / Zurückstufen (and Zu Dan umwandeln when eligible); each button is enabled purely by these functions — the UI embeds none of the rules. 17 unit tests lock the age boundaries.

Data manipulation 7 — Migration & seeding domain/migration.ts

migrate(data: AppData) → AppData is pure and runs on every load (and as the fresh-install seed). It:

  • seeds built-in Übungen + templates only when empty (factory defaults, fresh install) — existing data is kept, never auto-overwritten;
  • normalises game shape (drops legacy phase/neuroTarget; single sessionPhase → sessionPhases[]);
  • converts legacy athletes/contacts → persons + contactLinks; normalises legacy belts; backfills missing collections.
const data = stored ? JSON.parse(stored) : EMPTY_APP_DATA;
dispatch({ type: 'LOAD_ALL', payload: migrate(data) });   // one path for both install + upgrade

Persistence: DataContext writes the whole AppData to AsyncStorage under tkd_coach_app_data, debounced 300 ms after any state change.

Data manipulation 8 — Sync (QR transfer) utils/qrChunks.ts

The QR engine (@tobiasheinrichfaska/qr-sync) operates over named id-keyed collections. TKD-Coach configures:

games*groupspersons sessionPlanssessionLogsassessments sessionTemplates* contactLinks

* always shared (the library); the rest follow the coach's TransferSelection. The flat, id-referenced model is what makes change-detection and merge work: detectChanges diffs by id, applyChanges merges new/updated entities without touching unrelated ones.
