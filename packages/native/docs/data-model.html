Data Model & Data Manipulation

How TKD-Coach stores its data and the framework-free functions that read and change it. The whole model lives in one persisted object (AppData); all behaviour is driven by data and exercised by a pure, unit-tested domain layer that knows nothing about React.

Generated from source · src/types/index.ts, src/domain/*, src/context/reducer.ts. Keep in sync when the model changes.

Architecture — data-driven, logic/UI separation

Three layers, with a strict one-way dependency. The UI never embeds rules; rules never import the UI.

UI layer
src/screens/*, components
renders + dispatches
→
State layer
DataContext + reducer
holds AppState, persists
→
Domain layer
src/domain/*
pure rules & data

The UI dispatches actions and reads state; the reducer is the only writer of state; the domain layer is pure (no React, no storage, no UI) and is the single source of truth for catalogs, metric schemas, derived values and migration. This satisfies the workspace rule: the logic layer must run and be fully testable without any UI.

Where things live

  • types/index.ts — every interface
  • constants/games.ts — built-in Übungen + template seeds
  • context/reducer.ts — state transitions (the only writer)
  • context/DataContext.tsx — load, migrate, debounced persist
  • domain/* — metrics, catalogs, selectors, templates, migration

Core principle

Adding a metric, technique, body part or template means adding data — not writing new control flow. The assessment form, its validation, and the progress colour are all generated from METRIC_SCHEMAS.

Data manipulation 1 — Reducer actions

The reducer in context/reducer.ts is the only code that writes state. Every action returns a new state object (immutable; never mutates the previous one). Dispatch via useData().dispatch.

ActionPayloadEffect
SET_LOADEDbooleanToggle the loaded flag.
LOAD_ALLAppDataReplace whole state; set isLoaded=true.
ADD_GROUP / UPDATE_GROUPGroupAppend / replace by id.
DELETE_GROUP{id}cascade removes the group and all its athletes.
ADD_ATHLETE / UPDATE_ATHLETEAthleteAppend / replace by id.
DELETE_ATHLETE{id}cascade removes athlete, strips it from Group.athleteIds, deletes its assessments.
ADD_GAME / UPDATE_GAME / DELETE_GAMEGameDefinition / {id}Library CRUD.
ADD_SESSION_PLAN / UPDATE_SESSION_PLAN / DELETE_SESSION_PLANSessionPlan / {id}Plan CRUD.
ADD_SESSION_LOG / UPDATE_SESSION_LOG / DELETE_SESSION_LOGSessionLog / {id}Log CRUD (status changes go through UPDATE).
ADD_ASSESSMENT / DELETE_ASSESSMENTAssessment / {id}Assessment add/remove.
ADD_SESSION_TEMPLATE / UPDATE_SESSION_TEMPLATE / DELETE_SESSION_TEMPLATESessionTemplate / {id}Template CRUD.
 
const { dispatch } = useData();
dispatch({ type: 'ADD_ATHLETE', payload: athlete });
dispatch({ type: 'DELETE_GROUP', payload: { id: 'g1' } }); // also removes its athletes

Data manipulation 6 — Migration & seeding domain/migration.ts

migrate(data: AppData) → AppData is pure and runs on every load (and as the fresh-install seed). It:

  • refreshes built-in Übungen from BUILTIN_GAMES (new drills + new fields) while preserving user games;
  • refreshes built-in templates from BUILTIN_TEMPLATES while preserving user templates;
  • backfills collections missing on older saves (e.g. sessionTemplates on pre-template data).
const data = stored ? JSON.parse(stored) : EMPTY_APP_DATA;
dispatch({ type: 'LOAD_ALL', payload: migrate(data) });   // one path for both install + upgrade

Persistence: DataContext writes the whole AppData to AsyncStorage under tkd_coach_app_data, debounced 300 ms after any state change.

Data manipulation 7 — Sync (QR transfer) utils/qrChunks.ts

The QR engine (@tobiasheinrichfaska/qr-sync) operates over named id-keyed collections. TKD-Coach configures:

games*groupsathletes sessionPlanssessionLogsassessments sessionTemplates*

* always shared (the library); the rest follow the coach's TransferSelection. The flat, id-referenced model is what makes change-detection and merge work: detectChanges diffs by id, applyChanges merges new/updated entities without touching unrelated ones.

Testing

The domain layer is exhaustively unit-tested with ts-jest (no UI/Expo runtime needed) — per the workspace "intensive unit testing is mandatory" rule. Run from packages/native:

npx jest        # 42 tests across 6 suites
